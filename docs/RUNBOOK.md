# Запуск и обслуживание бота в Docker

Команды ниже выполняются из корня проекта, где лежит `docker-compose.yml`. Нужны запущенный Docker и Compose v2 (`docker compose version`).

## Первый запуск

1. Создайте `.env` из `.env.example`: `cp .env.example .env` (в PowerShell — `Copy-Item .env.example .env`). Если `.env` уже есть, не перезаписывайте его.
2. Оставьте `PORT` пустым или укажите `PORT=4003`: Compose пробрасывает порт хоста `4003` на порт контейнера `4003`. Для локальной игры задайте `BOT_TOKEN=` — браузерная страница не отправляет токен. Для арены укажите токен из кабинета, если он настроен. Не оставляйте значение-заглушку и не публикуйте `.env`.
3. Соберите образ, запустите сервис и проверьте, что процесс поднялся:

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 dots-bot
curl -fsS http://localhost:4003/v1/health
curl -fsS http://localhost:4003/v1/info
```

В Windows PowerShell используйте `curl.exe` вместо `curl`. `/v1/health` должен вернуть `{"status":"ok"}`, а `/v1/info` — версию бота и `specVersion: "v1"`. В текущем Compose нет `healthcheck`: статус `Up` подтверждает только запуск процесса, поэтому HTTP-проверку не пропускайте.

Если порт **хоста** занят, измените левую часть проброса, например на `"4004:4003"`, оставив `PORT=4003` внутри контейнера. В браузере и командах проверки тогда укажите `localhost:4004`. Браузерную игру открывайте отдельно через `web/index.html`: HTTP-сервер бота её не раздаёт.

Панель наблюдения открывается по `/` на локальном или публичном адресе бота. Задайте отдельный `DASHBOARD_TOKEN` в `.env` и введите его в панели, чтобы открыть историю. Метрики открыты, а история сбрасывается при перезапуске.

`SERVE_DASHBOARD=0` отключает раздачу страницы и её файлов. После изменения `.env` пересоздайте контейнер. Панель записывает данные после отправки ответа и не влияет на игру бота.

## Настройка и смена токена панели

- **Задать или сменить:** выполните `openssl rand -hex 24` в приватном терминале, запишите результат в `DASHBOARD_TOKEN` в `.env` и выполните `docker compose up -d --force-recreate dots-bot`. Откройте панель и войдите с новым токеном. Старый токен должен давать `401`. `BOT_TOKEN` для этого менять не нужно.
- **Потеря:** если есть доступ к серверу и нет подозрения на утечку, посмотрите значение в приватном терминале: `grep DASHBOARD_TOKEN .env`. Если значение недоступно или могло попасть к посторонним, задайте новый токен.
- **Утечка:** немедленно смените токен и пересоздайте контейнер. Проверьте, что старый токен больше не работает. Удалите раскрытое значение из доступных копий, где возможно, и передайте новый токен команде по защищённому каналу. Не копируйте токены или заголовок `Authorization` в журналы, тикеты и общий чат.
- **Отключить панель:** задайте `SERVE_DASHBOARD=0` в `.env` и пересоздайте контейнер. Это отключает только страницу и её файлы. Чтобы запретить доступ и к истории через API, также очистите `DASHBOARD_TOKEN`; тогда API истории вернёт `403`. `/api/status` останется открытым.

## Подключение к арене

Контейнер обслуживает HTTP. Для проверки из кабинета арены нужен публичный HTTPS-адрес без перенаправлений: например, настройте HTTPS на обратном прокси, который передаёт запросы в контейнер. `localhost` и адрес локальной сети доступны для локальной проверки, но не из кабинета арены.

Проверьте `/v1/health` и `/v1/info` по публичному адресу с другой сети. Затем укажите в кабинете базовый URL без `/v1/move` и выполните «Проверить API». Перед турниром сыграйте тренировочную партию за оба цвета и проверьте в журнале арены допустимость ходов, пропуски и время ответа с учётом сети. Лимит хода в первом раунде — 5 секунд. Формат запросов: [спецификация Arena v1](https://arena.projectset.ru/docs?p=dots) и [OpenAPI](https://arena.projectset.ru/docs?p=dots%2Fopenapi.yaml).

## Если арена сообщает о пропусках

```sh
docker compose ps -a
docker compose logs --tail=100 -f dots-bot
```

| Симптом | Что проверить |
|---|---|
| Контейнер не стартует или перезапускается | Наличие `.env`, ошибку сборки или запуска в логах и доступность порта хоста. |
| Локальный `/v1/health` отвечает, публичный — нет | DNS, TLS, настройки прокси, проброс порта, файрвол и редиректы. |
| `401` на `/v1/move` | Совпадает ли `BOT_TOKEN` с токеном в кабинете и передаёт ли прокси заголовок `Authorization`. Открытый `/v1/health` не проверяет токен. |
| `400` или `415` на `/v1/move` | JSON, `Content-Type: application/json` и формат позиции. HTTP API сейчас принимает только конечное поле. |
| `409` (`no_free_moves`) | На присланном поле не осталось свободных пересечений. |
| `5xx` или таймауты | Сравните локальное и публичное время ответа, посмотрите журнал арены, логи приложения и прокси. Бот пишет ошибки, но не ведёт журнал каждого HTTP-запроса. |

Если процесс нужно перезапустить без изменений кода и настроек, выполните `docker compose restart dots-bot`, затем снова проверьте `/v1/health`. Сохраните логи и позицию из журнала арены перед перезапуском, если разбираете сбой.

## Обновление и откат

### Автодеплой из main

Workflow `.github/workflows/deploy.yml` запускает полный `npm test` на Ubuntu с Node.js 20 и только после успешных тестов выкладывает точный проверенный коммит `main`. Подключение: SSH под `root`, папка `/root/dots-bot`, стандартный порт 22. Push в другие ветки не запускает деплой. Для включения workflow должен быть слит в `main`.

Однократная подготовка на сервере (если есть локальные изменения, сначала разберите их; `.env` сохраните):

```sh
cd /root/dots-bot
git status --short
git fetch origin main
git switch main
git pull --ff-only origin main
test -f .env
docker compose version
curl --version
```

Создайте отдельную пару SSH-ключей на доверенном компьютере: `ssh-keygen -t ed25519 -C github-actions-dots-deploy -f github_actions_dots` (без passphrase для автоматизации). Добавьте содержимое `github_actions_dots.pub` отдельной строкой в `/root/.ssh/authorized_keys` на сервере, не заменяя существующие ключи. Права: `chmod 700 /root/.ssh` и `chmod 600 /root/.ssh/authorized_keys`. Приватный ключ не коммитьте.

В GitHub → Settings → Secrets and variables → Actions добавьте repository secrets:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | IP или SSH-имя сервера, без `root@`, схемы и порта |
| `DEPLOY_SSH_KEY` | Полное содержимое приватного `github_actions_dots` |
| `DEPLOY_KNOWN_HOSTS` | Проверенная запись ключа SSH-хоста сервера |

Получите запись с доверенного компьютера командой `ssh-keyscan -t ed25519 АДРЕС_СЕРВЕРА > known_hosts`. Сверьте её отпечаток (`ssh-keygen -lf known_hosts`) с `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` через доверенную консоль сервера, затем сохраните содержимое `known_hosts` в secret. Для нестандартного порта добавьте `-p ПОРТ` в `ssh-keyscan` и repository variable `DEPLOY_PORT`. По умолчанию workflow использует 22.

Сервер также должен иметь доступ к `git fetch origin main`. Для публичного репозитория достаточно HTTPS origin. Для приватного настройте отдельный read-only deploy key для подключения сервера к GitHub. Это не тот ключ, которым Actions подключается к серверу.

`.env`, `BOT_TOKEN` и `DASHBOARD_TOKEN` остаются на сервере, workflow их не выводит. Рабочее дерево серверного клона должно быть чистым, текущая ветка — `main`: при расхождении деплой останавливается без принудительного сброса. Запуски выполняются последовательно; устаревший коммит не выкладывается. Пересоздание контейнера сбрасывает историю панели и кэш партий, поэтому слияния в `main` планируйте между играми.

После слияния откройте GitHub → Actions → «Проверка и деплой main». Повторный запуск доступен через Run workflow для `main`. Ошибка HTTP-проверки делает job красной, автоматического отката нет; используйте инструкцию отката ниже. Если права SSH-ключа больше не нужны, удалите его публичную строку из `authorized_keys` и соответствующий secret.

- **Новый код:** запустите `npm test` из исходников или `docker compose run --rm --no-deps dots-bot npm test` после сборки образа с новым кодом. Для выкладки выполните `docker compose up -d --build`, затем проверьте `/v1/health` и версию в `/v1/info`.
- **Изменение `.env`:** выполните `docker compose up -d --force-recreate dots-bot`. Обычный `restart` не подхватит новые переменные окружения.
- **Откат:** подготовьте отдельную копию известных рабочих исходников (например, сохранённый релиз или отдельный worktree). Перенесите в неё настройки без публикации `.env`. Остановите текущий сервис через `docker compose stop dots-bot`, чтобы освободить порт, и выполните `docker compose up -d --build` из рабочей копии. Проверьте версию и доступность по публичному адресу.

По возможности обновляйте сервис между партиями. Кэш ответов на повторы по `gameId` и `moveNo` хранится в памяти процесса и сбрасывается при перезапуске.

## Восстановление после паузы или обновления страницы

После 10 секунд без запросов `/v1/move` для конкретного `gameId` сервер сбрасывает кэш её ходов при следующем запросе. Ход рассчитывается по целиком присланной позиции; Docker не перезапускается, активные партии продолжают использовать свой кэш. Неизменность синих точек сама по себе не вызывает сброс.

Для новой партии клиент должен создавать новый `gameId`. В пределах десятисекундного окна конфликтующая позиция с прежними `gameId` и `moveNo` по-прежнему возвращает `409`; сброс по паузе не исправляет ошибки авторизации, формата запроса или сетевые тайм-ауты.

Проверка восстановления: `node --test tests/recovery.test.mjs`. Тесты проверяют сброс ровно на границе 10 секунд, допустимость нового хода, повторяемость ответа после восстановления, продление кэша запросами без новых синих точек и изоляцию активной партии.
