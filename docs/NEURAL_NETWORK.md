# Основа нейросетевой стратегии для «Точек»

## Что готово

Адаптер ai/strategy.js предназначен для будущей нейросети. В 0.5.0 сервер поддерживает два обученных линейных советника. Их форматы описаны в [руководстве](AI_INTEGRATION_GUIDE.md).

| Путь | Назначение |
|---|---|
| `ai/position.js` | Версионированный вход модели, маска свободных клеток, преобразование оценок в ход |
| `ai/strategy.js` | Адаптер `predict`, возврат к текущему алгоритму при ошибке модели |
| `tests/ai.test.mjs` | Кодирование, оба цвета, прямоугольное поле, запасной алгоритм и проверка результата |
| `server/move-worker.js` | Будущее место подключения стратегии после обучения и сравнения качества |
| `server/compute-move.js` | Существующий внешний контроль времени и отмены worker |

## Контракт модели v1

`encodePosition(request)` принимает конечное поле и возвращает:

- `version: 1`, `width`, `height`;
- `planes: Float32Array` — пять плоскостей в порядке `own`, `opponent`, `ownDead`, `opponentDead`, `last`;
- `legalMask: Uint8Array` — 1 для свободной клетки, 0 для занятой, включая мёртвые точки.

Порядок памяти: `[plane][y][x]`, индекс клетки `y * width + x`. `own` определяется по `request.you`. Плоскости `own` и `opponent` содержат все точки своего цвета, а плоскости dead дополнительно отмечают мёртвые. `last` отмечает последний ход, если он есть. Территория, таймеры и счёт в v1 не кодируются; при добавлении новых признаков нужно изменить версию контракта и переобучить модель.

`predict(input)` возвращает массив из `width * height` конечных чисел — логиты или оценки ходов, синхронно либо через Promise. Softmax не требуется. Занятые клетки и нечисловые оценки исключаются; при равенстве выбирается меньший индекс. Маска проверяет занятость и границы, а не качество захватов: правила окружений должна освоить модель или будущий поиск.

Пример только для эксперимента:

```js
import { createModelStrategy } from '../ai/strategy.js';

const choose = createModelStrategy({
  predict: async (input) => {
    // Здесь будущий ONNX/другой runtime: преобразование input в тензор,
    // запуск уже загруженной модели и извлечение policy-логитов.
    return new Float32Array(input.width * input.height);
  },
});
const move = await choose(request);
```

Нулевые оценки в примере не являются обученной стратегией. При отсутствии `predict`, исключении, неверном размере выхода или отсутствии пригодных оценок вызывается нынешний `chooseMove`. Для полного поля возвращается `null`, для неподдерживаемого входа — текущий алгоритм. Ошибка самого запасного алгоритма передаётся вызывающему коду.

## Как подключать позже

1. Выбрать поддерживаемые размеры поля и runtime. Прямоугольные поля кодируются, но совместимость конкретной модели с размером обязан обеспечить её адаптер.
2. Обучить модель и закрепить метаданные: версия входа, порядок плоскостей, размеры, версия правил, версия весов и контрольная сумма.
3. Сравнить её с текущим алгоритмом в воспроизводимых матчах: оба цвета, фиксированные seed, допустимость, победы/счёт и время p95/max.
4. Подключить адаптер внутри worker отдельной правкой. Инференс должен оставаться под внешним ограничением времени и отменой из `compute-move.js`. Этот модуль сам не прерывает зависший Promise: для возврата к алгоритму до общего дедлайна понадобится выделенный бюджет инференса и запас времени.
5. Сначала включать явно, сохранив текущий алгоритм по умолчанию и простой откат. Не выбирать путь модели или runtime из HTTP-запроса.

Worker сейчас создаётся на каждый ход. Большая модель будет загружаться заново; перед production нужно измерить это время и отдельно спроектировать жизненный цикл runtime. Персистентный пул workers в эту подготовку не входит.

## Данные для будущего обучения

В Docker Compose включён постоянный JSONL-архив успешных ходов. Формат реализован в `server/game-logs.js`: каждая запись содержит полную позицию до ответа бота, выбранный ход, время и источник. Токены, HTTP-заголовки и дополнительные поля запроса не копируются. Архив можно использовать для обучения на собственных играх методом imitation learning; он не является готовым обучающим пайплайном.

Порядок сохранения и команды выгрузки — [RUNBOOK: архив игр](RUNBOOK.md#архив-игр-для-обучения). `runId` меняется при старте процесса; `episodeId` группирует `gameId` внутри запуска. Если одна партия пережила перезапуск, при разбиении датасета дополнительно группируйте по `gameId`. Если клиент повторно использовал `gameId`, автоматическое различение партий пока не гарантируется.

Контракт обучающей позиции — одна позиция на строку (архив дополнительно содержит `runId`, `gameId`, `moveNo`, время и ответ):

```json
{"schemaVersion":1,"episodeId":"local-episode-1","split":"train","position":{"you":"red","field":{"width":3,"height":3},"points":{"red":[],"blue":[]},"dead":{"red":[],"blue":[]},"last":null},"target":{"action":4,"outcome":1},"source":{"kind":"self-play","rulesVersion":"to-be-pinned","teacherVersion":"to-be-pinned"}}
```

`action` — `y * width + x`. `outcome` — итог с точки зрения `position.you`: победа 1, ничья 0, поражение -1. Архив всегда пишет `null`: API хода не сообщает подтверждённый результат. Итог нужно дополнить из журнала арены или проверенного движка, его нельзя выводить из промежуточного счёта. Ходы текущего алгоритма помечены как `teacher`, а не как доказанно оптимальная игра. Повторные запросы остаются отдельными записями: перед обучением удалите дубликаты по позиции и действию, отдельно обработайте `source.fallback`.

Все позиции одной партии должны попадать только в один split (`train`, `validation` или `test`), чтобы не было утечки между выборками. Вход кодируется тем же `encodePosition`, которым пользуется инференс. Перед обучением сверить правила с эталонным движком арены; нынешняя история панели ограничена памятью и не заменяет датасет с подтверждённым результатом.

Весовые файлы и датасеты хранить отдельно от Git (например, release assets или внешнее хранилище), фиксируя версию и checksum. Секреты в артефакты и метаданные не включать.
